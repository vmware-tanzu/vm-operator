# Implementation Plan: VirtualMachineInfraMigration Status on VirtualMachine

- **Spec**: [`spec.md`](./spec.md)
- **Model**: [`model.md`](./model.md)

## Summary

Add a controller that watches `VirtualMachineInfraMigration` resources from the mobility operator and mirrors the `Ready` condition of each, when it describes the migration's current generation, onto the VirtualMachine with the same namespace and name, as a `VirtualMachineInfraMigrationReady` condition. When the migration is ready, it also sets a new `status.volumeAttributesClassName` field on the VirtualMachine. When the migration is deleted, the controller removes the mirrored condition, and it never clears `status.volumeAttributesClassName`. The controller only starts when the `StoragePolicyMutability` feature is enabled. The migration only carries the home directory's storage policy ID, so the controller looks up the VolumeAttributesClass for that policy and records it only if it is also the one in the VirtualMachine's spec. This change also stops the crypto reconciler from encrypting an existing VirtualMachine, or the disk of an attached PVC, from the storage policy of its VolumeAttributesClass, since the migration does it, and re-keys them once the migration is complete (vmop-4461, vmop-4463, and vmop-4464).

## Technical context

- **Go**: as pinned by the root `go.mod`.
- **API versions**: adds condition constants and the `status.volumeAttributesClassName` field to `v1alpha6`. Consumes `mobility-operator.vmware.com/v1alpha4` (`VirtualMachineInfraMigration`).
- **Modules**: the root module now requires `external/mobility-operator` (with a `replace`), because a root package imports its API. `external/mobility-operator` remains its own Go module, and its `go.mod` and `go.sum` are unchanged because `v1alpha4` depends only on `k8s.io/apimachinery`.
- **Feature flag**: `pkgcfg.Features.StoragePolicyMutability`, driven by the existing storage policy mutability capability. No new flag.

## Constitution check

- **Controllers are thin; logic in `pkg/`**: the logic is a condition mirror of under 100 lines, kept in the reconciler, matching the `VolumeAttributesClass` controller which this controller is modeled on. If it grows, it moves to `pkg/`.
- **No direct vSphere calls**: none are made.
- **Crypto logic stays in `pkg/`**: the crypto reconciler change is in `pkg/vmconfig/crypto`, and the storage-policy checks are shared helpers in `pkg/util/kube` that the VirtualMachine controller and the validation webhook only call.
- **`status.observedGeneration` and a `Ready` condition**: not applicable. The controller does not own a resource. It writes the mirrored condition on a VirtualMachine whose status is owned by the VirtualMachine controller, and it never writes the migration resource.
- **Shared list-typed field**: `status.conditions` on the VirtualMachine is written by several controllers. The controller uses `pkg/patch.Helper`, which re-reads the latest VirtualMachine, applies only the changed conditions, and patches with an optimistic lock, retrying on conflict. The mirrored condition is `VirtualMachineInfraMigrationReady`, which no other controller writes, so the controller declares it as owned (`patch.WithOwnedConditions`) and the helper writes or removes it without treating a concurrent change as a conflict. This satisfies the fan-in rule in the constitution. `status.volumeAttributesClassName` is a scalar that only this controller writes, so it needs no optimistic lock: the helper's merge patch sends only that field and cannot drop another writer's change. If the spec changes between the read and the write, the VirtualMachine event it causes reconciles the migration again and corrects the field, or finds that the class no longer matches and writes nothing.
- **Controllers for other API groups are not placed directly in `controllers/`**: the controller lives under `controllers/mobility/`.
- **Tests**: one `_test.go` and one `_suite_test.go` per package, labels from `pkg/constants/testlabels`.
- **E2E**: scoped as a follow-up tracked by vmop-4499, see Test strategy. This is the explicit exception allowed by `e2e-sync-with-changes.md` and is called out in the PR description.

## API / CRD strategy

Additive only, in `v1alpha6`: condition type constants, which need no schema change because conditions are opaque strings, and one optional string field, `status.volumeAttributesClassName`, which changes the `VirtualMachine` CRD schema and is regenerated with `make generate-manifests`. No version bump is needed. Each older version already has a manual `VirtualMachineStatus` converter, and its `ConvertTo` restores the whole hub `status` from the conversion annotation, so the new field round-trips without a restore function. `make generate-go-conversions` only adds a `does not exist in peer-type` warning line to each older version's generated file. The conversion round-trip suites in `api/test` pass with the field.

The `spec.crypto.encryptionClassName` documentation also changes, to say that the storage policy that must be encryption-enabled is the one of `spec.volumeAttributesClassName` when it is set. That is documentation only: no schema change, no version bump, and no conversion work. The CRDs are regenerated with `make generate-manifests`, and the `v1alpha6` API reference is updated from the same comment.

## Controller impact

- **Watches**: `VirtualMachineInfraMigration` (primary), `VirtualMachine`, and `VolumeAttributesClass`. A VirtualMachine event is mapped to the migration with the same namespace and name. It is dropped when no such migration exists and the VirtualMachine does not have the mirrored condition, so most VirtualMachine events cost one cache read. A VirtualMachine that still has the condition is enqueued so that it is removed, which also covers a migration that was deleted while VM Operator was not running, since the VirtualMachine's create event at startup passes the predicate. Any other error is logged and the migration is enqueued anyway, so the reconciler retries instead of the event being dropped. The VirtualMachine watch covers the case where the migration's `Ready` condition was set before the VirtualMachine existed, and a predicate passes only a create, a delete, a generation (spec) change, and a change to the mirrored `Ready` condition, so that the controller's own status patch and the VirtualMachine controller's status writes do not reconcile the migration. A VolumeAttributesClass is mapped to the migrations whose `spec.targetStorage.homeStoragePolicyID` is the storage policy it refers to, using a field index on that field, and a predicate passes only its creation, since its parameters are immutable and the recorded class is never cleared.
- **VolumeAttributesClass lookup**: for a ready migration with `spec.targetStorage.homeStoragePolicyID`, the controller lists the cluster's VolumeAttributesClasses through the manager's cache and keeps those whose `parameters["storagePolicyID"]` matches (`kubeutil.GetVACNamesForStoragePolicyID`). If the VirtualMachine's `spec.volumeAttributesClassName` is one of them, it is written to `status.volumeAttributesClassName`. Otherwise nothing is written and the reason is logged at verbosity 2, since this most likely means that the spec was edited again and the mobility operator has not picked it up yet, and the controller waits for the next change to the VirtualMachine's spec, the migration, or the VolumeAttributesClasses, all of which it watches, instead of requeueing. A failure to list is returned so the reconcile is retried. The `Ready` condition is still mirrored in the mismatch cases. A VolumeAttributesClass that appears later reconciles the migrations that refer to its policy, because it is watched.
- **Reconcile**: the migration's `Ready` condition is mirrored onto the VirtualMachine as `VirtualMachineInfraMigrationReady`, with its status, reason (or the status when it has none), and message followed by a `@ VirtualMachineInfraMigration/<name>` reference (the reference alone when it has no message). A message that would not leave room for the reference within the 32768 characters of a condition message is truncated on a character boundary and ends in `...`, so the reference is always present and the API server does not reject the status patch. It is mirrored only when it describes the current generation, i.e. its `observedGeneration` is at least the migration's `metadata.generation` (`conditions.GetObservedAt(obj, obj.Generation)`), so a `Ready` condition without an `observedGeneration` is never mirrored. A `Ready` condition that is behind describes the previous spec, so it is not mirrored and the mirrored condition is removed, as it is when the migration no longer reports `Ready`. When the migration's spec changes, the VirtualMachine therefore drops the outcome of the previous spec until the migration reports `Ready` for the new generation, instead of briefly reporting a stale `True`. The migration's other conditions are not mirrored, so the VirtualMachine API does not depend on the mobility operator's condition vocabulary, and the `observedGeneration` is not copied. A migration is considered ready only when `conditions.IsReady(obj, conditions.WithGeneration(obj.Generation))` is true, i.e. its `Ready` condition is `True` and its `observedGeneration` is at least its `metadata.generation`, and only then is `status.volumeAttributesClassName` resolved and recorded. A missing or deleting VirtualMachine is skipped without error. When the migration does not exist (`ReconcileDelete`), the mirrored condition is removed from the VirtualMachine with the same namespace and name, through the same patch helper and owned condition, because it would otherwise describe a resource that no longer exists. A VirtualMachine that is being deleted is skipped. `status.volumeAttributesClassName` is never cleared.
- **No pause and no validation**: the controller does not pause the reconciliation of a VirtualMachine while a migration for it exists and is not ready, and no webhook rejects a change to `spec.volumeAttributesClassName` while the migration is running. The VirtualMachine reconcile already skips a VirtualMachine's spec while a task is running on it in vSphere (`ErrHasTask` in `pkg/providers/vsphere/vmprovider_vm.go`), which is enough to avoid concurrent operations, so this change adds nothing for it.
- **Crypto reconciler under a VolumeAttributesClass**: an existing VirtualMachine that specifies `spec.volumeAttributesClassName` is under a VolumeAttributesClass. A new VirtualMachine never is, since no migration exists for it, so the create path is unchanged. The migration applies the storage policy of such a VirtualMachine and the encryption that policy requires, so the reconciler does not encrypt it because that storage policy is encrypted, and writes no storage profile on its disks (the fast-deploy encryption of disks is skipped), since for the VM home and PVC-backed disks either would duplicate the migration and could race with it. The fast-deploy encryption only targets disks with no PVC, which the migration does not cover, so under a VolumeAttributesClass they are left as they are, a limitation the mobility operator's design lists. It still encrypts for a vTPM, exactly as under a StorageClass, and still takes whether the VirtualMachine is encrypted from the VolumeAttributesClass's storage policy (`kubeutil.IsEncryptedStoragePolicyForVM`), which is what lets a VirtualMachine the migration encrypted pass validation without a vTPM or an encrypted StorageClass. The disk of an attached PVC follows the same rules: a PVC is under a VolumeAttributesClass when it specifies one and the capability is enabled (`kubeutil.IsPVCUnderVAC`), its storage policy comes from `kubeutil.IsEncryptedStoragePolicyForPVC`, and its unencrypted disk is skipped before its key is resolved, since there is no key to apply.
- **Re-key hold**: the existing re-key paths, for the VM home (EncryptionClass and default key provider) and for attached PVC disks, are kept and write no storage profile. Each is held while its object's change is in progress, that is while the observed class (`status.volumeAttributesClassName`, or the PVC's `status.currentVolumeAttributesClassName`) is not empty and is not the class in its spec. The hold is per object, not the VirtualMachine's change for its PVCs, since the migration records each class when it completes. An empty observed class counts as in sync, because only a completed migration records one, so the first migration of an object to a class is not held. A held re-key is logged at verbosity 4. The VirtualMachine and PVC watches have no predicate, so the status write that records the class reconciles the VirtualMachine and the re-key follows. While a re-key is held, `VirtualMachineEncryptionSynced` is not touched and still reports from the crypto state. Reporting it from the migration is vmop-4465, and a TODO in the reconciler marks the place.
- **Webhook and VirtualMachine controller**: `validateCrypto`, and the VirtualMachine controller's fast-deploy check, which runs when fast deploy is enabled and BYOK is not, call `kubeutil.IsEncryptedStoragePolicyForVM`. So `spec.crypto.encryptionClassName` is validated against the storage policy of `spec.volumeAttributesClassName` when it is set, with its own message (`requires spec.volumeAttributesClassName specify an encryption storage policy`), and the controller's check reads the same storage policy. An error resolving the VolumeAttributesClass is logged and returned as it is, not ignored, by these and by the crypto reconciler. No RBAC is added, since the VolumeAttributesClass reads are already granted.
- **Logging**: a successful reconcile is logged at verbosity 4. It is logged at Info only when the status of the mirrored condition changes, including it being added or removed, or when `status.volumeAttributesClassName` is newly recorded, and the entry names the change as `<type>: <before> -> <after>` and the recorded class. A change that is only to the condition's reason or message, an unchanged class, and an idle reconcile are not logged at the default verbosity, so that reconciling an unchanged migration does not write to the log. When a ready migration's home storage policy is not referenced by the spec's VolumeAttributesClass, the reason is logged at verbosity 2.
- **RBAC**: `get;list;watch` on `virtualmachineinframigrations` in `mobility-operator.vmware.com`, `get;list;watch` on `volumeattributesclasses` in `storage.k8s.io` (already granted for the `VolumeAttributesClass` controller), and `get;list;watch` on `virtualmachines` plus `get;update;patch` on `virtualmachines/status` in `vmoperator.vmware.com`. The VirtualMachine rules already exist, so only the migration rule is new in `config/rbac/role.yaml`.
- **Scheme**: the mobility v1alpha4 scheme is registered in the manager only when the feature is on, like the other feature-gated external APIs.
- **Known risk**: a controller `For()` a kind whose CRD is absent fails to start, which would stop VM Operator. The feature gate is the only protection, and it is enough because the spec guarantees that the CRD is installed whenever the capability is enabled.
- **Unresolvable VolumeAttributesClass**: a VirtualMachine whose `spec.volumeAttributesClassName` cannot be resolved, for example because the class was deleted, is not reconciled until it can be, since the error is returned and not ignored. With fast deploy enabled and BYOK disabled that includes its deletion, because the controller's check runs before the delete branch.
- **Disks with no PVC under a VolumeAttributesClass**: neither this reconciler nor the migration encrypts them, so with fast deploy they are no longer encrypted with the StorageClass's profile once a VirtualMachine specifies a class. The mobility operator's design lists the migration's side as a limitation, and the story for this behavior (vmop-4461) requires that VM Operator apply no storage policy under a VolumeAttributesClass.

## Build and generation

- `make generate-go` generates deepcopy for `external/mobility-operator/...` using the same form as every other external module. This is possible because the root module now imports the package, so `go mod tidy` keeps the `require`. This also updates the v1alpha2 deepcopy file's license header to the repository boilerplate.
- `make generate-external-manifests` generates the test-only CRD for `mobility-operator/api/v1alpha4` only. v1alpha2 holds `ImportOperation`, which only the E2E tests use, and generating over both versions would also emit an `importoperations` CRD that no envtest suite needs.

## The `v1alpha4` API package

`external/mobility-operator/api/v1alpha4` contains only what this controller consumes: the `VirtualMachineInfraMigration` types, the group-version registration, and the generated deepcopy. Like the other `external/*` modules, it is not a full copy of the owning operator's API. The mobility operator also defines `ImportOperation`, `StoragePolicyChange`, and related types in `v1alpha4`, which are deliberately not copied because nothing in this repository uses them. Adding one later means adding its types here and regenerating. The package carries the repository license header, and has no `Hub()` conversion stubs or `SetConditions` because nothing in this repository converts or writes these objects.

## Rollout

- **Feature gate**: off unless the existing `StoragePolicyMutability` capability is enabled. No new flag or default. When it is off the controller is not started and the `VirtualMachineInfraMigration` scheme is not registered.
- **Older API versions and clients**: the change is additive in `v1alpha6`, one optional string status field and condition types, which are free-form strings. `v1alpha1` to `v1alpha5` do not have the field, and the existing conversion round-trip suites for them pass with it.
- **Existing objects after upgrade**: VirtualMachines without a same-name migration are unchanged, and the new field is omitted when empty. With the capability enabled, a migration that already exists is mirrored when the controller first reconciles it.
- **Version skew and rollback**: the controller needs the `VirtualMachineInfraMigration` `v1alpha4` CRD, which the spec treats as guaranteed whenever the capability is on. After a rollback the mirrored condition remains on the VirtualMachines. The behavior of an older `VirtualMachine` CRD schema for the new field was not tested.
- **Encryption under a VolumeAttributesClass**: only a VirtualMachine that specifies `spec.volumeAttributesClassName`, or a PVC that specifies it while the capability is enabled, behaves differently, so existing objects are unchanged after an upgrade. A VirtualMachine or PVC without a class is encrypted and re-keyed from its StorageClass as before.
- **Release note**: when the `StoragePolicyMutability` capability is enabled, VM Operator does not encrypt an existing VirtualMachine, or the disk of an attached PVC, from the storage policy of its VolumeAttributesClass, since the storage policy migration does it. It still encrypts for a vTPM, and it re-keys the VirtualMachine and its attached PVCs once the migration is complete. A disk that has no PVC, such as a fast-deploy disk, is not covered by the migration, so it is no longer encrypted from the storage policy of a VolumeAttributesClass.
- **Release note**: when the `StoragePolicyMutability` capability is enabled, a VirtualMachine mirrors the `Ready` condition of its `VirtualMachineInfraMigration` as the `VirtualMachineInfraMigrationReady` condition, and reports the VolumeAttributesClass it was migrated to in the new `status.volumeAttributesClassName` field.
