# Research: Tag CRD + Tag Controller for Affinity

- **Spec**: [`spec.md`](./spec.md)
- **Epic**: vmop-3882
- **Date**: 2026-08-04

This is the investigation log behind [`spec.md`](./spec.md), [`plan.md`](./plan.md), and [`model.md`](./model.md). It records the prior art in this repository, the platform semantics the design depends on, and the decisions taken (with the alternatives rejected).

## Prior art in this repository

### Mechanism A — create-time label→tag conversion (`affinity.go`)

`pkg/providers/vsphere/virtualmachine/affinity.go` holds today's label-to-tag conversion:

- `extractAffinityLabelsFromVM(vmCtx, constraints) sets.Set[string]` walks `vm.Spec.Affinity.VMAffinity` and `.VMAntiAffinity`, both the `RequiredDuringSchedulingPreferredDuringExecution` and `PreferredDuringSchedulingPreferredDuringExecution` term lists, and returns the referenced labels as `"key:value"` strings. Terms are skipped when their `TopologyKey` is not eligible under the passed `AffinityRuleConstraints`.
- `genConfigSpecTagSpecsFromVMLabels(vmCtx, configSpec, constraints)` intersects the VM's **own** labels (after `kubeutil.RemoveVMOperatorLabels`) with that set, and appends one `vimtypes.TagSpec` per survivor with `Operation: add` and `Id.NameId = {Tag: "<key>:<value>", Category: vm.Namespace}`.
- `extractLabelsFromSelector` supports `matchLabels` and `matchExpressions` with the `In` operator only; any other operator returns an error which callers log at V(4) and skip. Labels are emitted in `"key:value"` form and sorted.

Call sites are both in `pkg/providers/vsphere/virtualmachine/configspec.go`: once in `CreateConfigSpec` (line ~158) and once in `CreateConfigSpecForPlacement` (line ~318). `CalculateAffinityConstraints(vmCtx, isCreateVM)` (line ~351) derives the constraints from `Features.VMPlacementPolicies` (zone rules), `Features.VMAffinityDuringExecution` (host rules), CAPI/VKS labels, and the presence of a zone label.

Those two functions serve **four** purposes, which matters because the flag-on replacement differs per purpose (D17). `CreateConfigSpec` has three callers in `pkg/providers/vsphere/vmprovider_vm.go` — `createArgs` (line ~2581), `updateArgs` (~3274) and `resizeArgs` (~3340) — and `CreateConfigSpecForPlacement` has two, `vmprovider_vm.go` (~1786) and `vmprovider_vmgroup.go` (~245). The `updateArgs` / `resizeArgs` ConfigSpecs flow into `doReconfigure`, which is where this feature's own emission happens; the placement ConfigSpec is sent only to the placement API and is never persisted. Both functions are **pure** — neither takes a `ctrlclient.Client` — so anything that has to read `Tag` resources must be called from the provider methods instead.

Limits of **today's** behavior that motivate this feature, acknowledged in the existing code comments (including a `TODO(for Day 2 operations)`). These describe mechanism A as it stands, not a constraint this feature inherits:

1. Only labels referenced by the VM's **own** `spec.affinity` become tags — a VM that carries the label but declares no affinity is never tagged, so it silently misses the relationship.
2. Mechanism A is **add-only**: every `TagSpec` it emits uses `Operation: add`, so a label that stops participating never has its tag removed. Note it *is* reached on the update and resize paths via `CreateConfigSpec`'s other two callers — the `TODO` comment says as much — so the gap is not that updates are unreachable but that they cannot converge *downward*. The `Tag`-driven path emits both `ArrayUpdateOperationAdd` and `ArrayUpdateOperationRemove` (see "`TagSpec` supports removal, so tags can be diffed" below), which is what makes spec G5 and US3 achievable.

Both call sites also emit `genConfigSpecAffinityPolicies`, which builds the `VmPlacementPolicies` (`VmVmAffinity`, `VmVmAntiAffinity`, `VmToVmGroupsAntiAffinity`) that *consume* these tags. That part is out of scope here (spec NG5).

### Mechanism B — UUID-based tagging via the vSphere Policy reconciler

`pkg/vmconfig/policy/` (`policy_reconciler.go`, `policy_reconciler_util.go`) creates a `vspherepolv1.PolicyEvaluation` per VM (named `vm-<vmName>`) via `controllerutil.CreateOrPatch`, feeding it image name/labels, guest ID/family, workload labels, and explicitly-referenced policies, then consumes the results. `vspherepolv1.TagPolicySpec.Tags` carries **UUIDs** of vSphere tags to apply. This is the UUID-based path referenced in the source spec.

This feature coexists with mechanism B: it neither reads nor writes `PolicyEvaluation`/`TagPolicy`, and the two produce disjoint `TagSpec` entries (UUID-identified vs. name+category-identified).

### The `vmconfig.Reconciler` extension point

`pkg/vmconfig/vmconfig_reconciler.go` defines:

```go
type Reconciler interface {
    Name() string
    Reconcile(ctx, k8sClient ctrlclient.Client, vimClient *vim25.Client,
        vm *vmopv1.VirtualMachine, moVM mo.VirtualMachine,
        configSpec *vimtypes.VirtualMachineConfigSpec) error
    OnResult(ctx, vm, moVM, resultErr error) error
}
```

This is the only extension point in the VM reconcile path that has **both** a Kubernetes client and the outgoing `ConfigSpec` in hand — exactly what the Tag-driven path needs (read/write `Tag` resources, then emit `TagSpecs`). Existing implementations: `crypto`, `diskpromo`, `bootoptions`, `extraconfig`, `networkextraconfig`, `policy`, `cdrom`, `volumes`, `virtualcontroller`, `anno2extraconfig`.

**Registration and dispatch are two separate things here, and only registration is visible in the controller.** `controllers/virtualmachine/virtualmachine/virtualmachine_controller.go` `Reconcile` (~line 342) builds a registry in the context:

```go
ctx = vmconfig.WithContext(ctx)
if pkgcfg.FromContext(ctx).Features.BringYourOwnEncryptionKey {
    ctx = vmconfig.Register(ctx, crypto.New())
}
...
ctx = vmconfig.Register(ctx, bootoptions.New())
```

That registry has exactly one consumer — the `OnResult` loop in `pkg/providers/vsphere/session/session_vm_update.go:136`, itself gated on `Features.BringYourOwnEncryptionKey || Features.TelcoVMServiceAPI`:

```go
features := pkgcfg.FromContext(vmCtx).Features
if features.BringYourOwnEncryptionKey || features.TelcoVMServiceAPI {
    for _, r := range vmconfig.FromContext(vmCtx) {
        if err := r.OnResult(vmCtx, vmCtx.VM, vmCtx.MoVM, updateErr); err != nil {
```

`Reconcile` is **never** dispatched through the registry. Each reconciler runs from a hardcoded, individually flag-gated call site inside `doReconfigure` (`session_vm_update.go:1485+`): `reconcileDiskPromo`, `reconcileCrypto`, `reconcileRegisterUnmanagedDisks`, `reconcileBootOptions`, `reconcileAnnotationsToExtraConfig`, `reconcileAdvancedExtraConfig`, `reconcileNetworkExtraConfig`, `reconcileVSpherePolicies`, `reconcileVirtualControllers`, `reconcileCdrom`. Consistent with that, `policy`, `cdrom`, `volumes`, `virtualcontroller` and `anno2extraconfig` are never `Register`ed at all — they exist only as package-level `Reconcile` functions with call sites. `pkg/vmconfig/policy` shows the full shape: a package-level `Reconcile` (line 36) alongside `New()` (line 51) and the interface method (line 68).

Two consequences for this feature, both recorded as D11:

1. Adding a call site in `doReconfigure` is mandatory; registering the reconciler is optional and by itself does nothing under `TaggingAPI`.
2. Because the call sites are individual, a reconciler can be split across more than one of them — which is what lets `Tag` bookkeeping run before `reconcileVSpherePolicies` and tag-spec emission run after it.

The reconcilers run **before** `doReconfigure`'s `apiEquality.Semantic.DeepEqual(configSpec, defaultConfigSpec) → return nil` short-circuit (~line 1613), so `Tag` bookkeeping still happens on a reconcile where nothing else about the VM changed.

`moVM` gives the reconciler the VM's live state, including its `Config.ExtraConfig` — which is what makes an add/remove **diff** possible for this feature rather than blind adds. The VM update flow also fetches the VM's attached tags as step 3 of the documented reconcile order in `operator-best-practices.md` ("VM Update Reconcile Order"), but this feature cannot use them: they do not arrive on `moVM` and are not name+category identified. See "The attached-tag list is UUIDs and is not on `moVM`" below.

### Waking the affected VMs: `Watches` + mapper, not `cource`

Two mechanisms in this repository can enqueue a VM reconcile in response to something other than a change to the VM itself.

**`Watches` with a mapper function** is the ordinary one, and the VM controller already uses it four times in `AddToManager`: `VirtualMachineClass`, `EncryptionClass` (gated on `Features.BringYourOwnEncryptionKey`), `VirtualMachineImageCache` (gated on `Features.FastDeploy`), and PVCs. `operator-best-practices.md` ("Mapper Functions") specifies the shape, including the requirement that the mapper's `List` be served by a field index and `client.MatchingFields` rather than an unfiltered namespace list. `pkg/util/vmopv1/vm.go`'s `EncryptionClassToVirtualMachineMapper` is the closest precedent: same signature, same feature-gated registration, same "find the VMs that reference this object" job.

**`pkg/util/kube/cource`** is a registry of `chan event.GenericEvent` held on the controller-manager context (created once in `main.go:201`), consumed via `WatchesRawSource(source.Channel(...))` and fed by a producer that looks up the same key. Every non-test producer in the tree is reacting to something that is *not* a Kubernetes object event and therefore cannot be watched: `services/vm-watcher` reacting to a vCenter property-collector change, and `vmprovider_vm.go:2211` reacting to a datastore file it discovered missing several layers below any controller. The `"VirtualMachine"` consumer is gated on `pkgcfg.FromContext(ctx).AsyncSignalEnabled` (default `true`), and so is every producer of it.

This feature's trigger *is* a Kubernetes object event — a write to a `Tag` — so it takes the ordinary mechanism (D19). Three consequences that mattered to the decision:

- **Durability.** A `cource` channel is in-memory and has no replay: events queued before a manager restart are simply gone. An informer re-lists on start and delivers a Create event for every existing object, so a watch-driven fan-out self-heals across a restart.
- **No flag coupling.** A `cource`-based fan-out would only work when `AsyncSignalEnabled` is true, and — because the send is a bare channel write — a `Tag` controller producing into an undrained buffered channel would block a reconcile worker forever once 100 events had accumulated. The watch has no such failure mode.
- **A predicate is now required.** The cost of a watch is that *every* `Tag` write becomes an event, including the `Tag` controller's own status/label-mirror writes and the VM path's owner-reference patches. With `cource` the producer chose when to fan out; with a watch that choice moves into a predicate. `spec` is immutable by admission and the mapper's key derives from `spec` alone, so the predicate is small: create and delete only — `Tag` carries no finalizer (D10), so deletion is atomic and there is no separate `deletionTimestamp` transition to admit. See `plan.md` "Fan-out — the VM controller's `Tag` watch".

### `vsphere.policy.vmware.com` API and its manifests

`external/vsphere-policy/` is its own Go module (`github.com/vmware-tanzu/vm-operator/external/vsphere-policy`), aliased `vspherepolv1`, group `vsphere.policy.vmware.com`, version `v1alpha1`. Existing types: `ComputePolicy`, `TagPolicy`, `PolicyEvaluation`, plus shared matcher types in `common_types.go`. Each type appends itself to `objectTypes` in an `init()`; `groupversion_info.go` wires `AddToScheme`.

CRD manifests for this module are generated into `config/crd/external-crds/` by `make generate-external-manifests`, which already runs `controller-gen` over `paths=github.com/vmware-tanzu/vm-operator/external/vsphere-policy/...`. The existing outputs are `vsphere.policy.vmware.com_computepolicies.yaml`, `_policyevaluations.yaml`, and `_tagpolicies.yaml` — so a new type in the module is picked up with no Makefile change.

A new external type has to be taught to four places, and only two of them are obvious:

- `test/builder/fake.go` (`KnownObjectTypes`) — so the fake client enforces the status-subresource split in unit tests. Envtest needs nothing: `test/builder/test_suite.go` loads the whole `config/crd/external-crds` directory.
- `config/default/kustomization.yaml` — the Supervisor install kustomization lists each external CRD **by path** (lines 11-19). `config/crd/external-crds/README.md` documents that list as the "Production CRDs" set; CRDs absent from it are test-only.
- `pkg/crd/crd.go` `Install`, called from `main.go`'s `initCRDs` at pod startup, which creates-or-deletes each embedded CRD according to the current feature flags. Its `switch` on CRD kind ends in `default:` with `enabled = true`, so a kind nobody added a `case` for is installed **unconditionally** — no error, no warning. The three existing `vsphere.policy` kinds share a `case` gated on `features.VSpherePolicies`, so they are deleted when that flag is off; a new flag-gated kind wants the same treatment (D14).
- `config/crd/crd.go`'s embed directives — but **not** for this feature: `//go:embed external-crds/vsphere.policy.vmware.com_*.yaml` is a glob, so a new file in that group is embedded automatically. A new *group* would need a new directive.

The useful consequence of the `pkgcrd.Install` gate is that CRD presence becomes an accurate cluster-observable proxy for the feature flag, which is what the E2E suite gates on until the `PlacementPoliciesForVMServiceVmsV3` capability lookup lands (spec G13).

Controllers for this group live under `controllers/vspherepolicy/` (currently only `policyevaluation/`), registered from `controllers/vspherepolicy/controllers.go`, which is itself called from `controllers/controllers.go` (~line 91). This matches the constitution's rule that controllers for non-`vmoperator.vmware.com` groups are not placed directly in `controllers/`.

### `spec.affinity` is immutable; labels are not

`webhooks/virtualmachine/validation/virtualmachine_validator.go`:

- `validateVMAffinity` (~line 3262) validates the shape on create and already branches on `Features.VMAffinityDuringExecution` for host-topology terms.
- `validateImmutableVMAffinity` (~line 3463) is called from the update path (~line 2497) and forbids **any** change to `spec.affinity`, with **no** feature gate:

```go
if !equality.Semantic.DeepEqual(vm.Spec.Affinity, oldVM.Spec.Affinity) {
    allErrs = append(allErrs, field.Forbidden(p, "updating Affinity is not allowed"))
}
```

This feature leaves that check exactly as it is (spec NG8, D7 below). `metadata.labels`, by contrast, is freely mutable — `validateLabel` (~line 2739) restricts one reserved key, `vmopv1.PausedVMLabelKey`, and only for non-privileged accounts — and ownership requires a VM to carry the label **as well as** reference it. So a live VM's participation in a label pair does change, by relabeling rather than by re-affinitizing, and the convergence US3 specifies is reachable without touching the immutability rule.

## Platform semantics the design depends on

### Owner-reference garbage collection does **not** cover "ownership dropped to zero"

Kubernetes garbage collection deletes a dependent when the owners named in its `ownerReferences` are **deleted**. It does not delete an object merely because its `ownerReferences` list became empty while those owners still exist — such an object is treated as an orphan and is retained indefinitely.

Two clients do this work, and neither is a privileged account by VM Operator's definition: `system:serviceaccount:kube-system:generic-garbage-collector` deletes the dependent when its owners are gone **and patches the dependent to prune a dangling owner reference** when one owner is deleted while others remain; `system:serviceaccount:kube-system:namespace-controller` deletes namespaced resources during namespace teardown. `IsPrivilegedAccount` (`pkg/builder/auth.go:42`) matches neither, so a validating webhook that restricts UPDATE/DELETE to privileged accounts denies both. See D15 and `model.md` "V6's system-account allow-list".

Consequence: the source spec's note that an empty owner-reference list means "GC deletes the `Tag`" does not hold even on the VM-deletion path (spec US1 scenarios 5-6, US2 scenario 2), because `ReleaseOwnership` empties the owner list explicitly, during the deleted VM's own reconcile, **before** its finalizer is released and the object is actually removed — GC's cascading delete only reacts once the owner object itself is gone, so by the time GC would look, the reference is already gone and the list is already empty with the VM still (briefly) present. This needs an **explicit delete**. The design assigns that delete to the `Tag` controller, which already watches `Tag` and can observe the empty list; ordinary GC remains as the backstop for an owner reference stranded outside this explicit path. This is recorded as an edge case in `spec.md` and specified in `plan.md`.

Ownership is driven solely by each VM's own (immutable) `spec.affinity`, so — unlike an earlier version of this design — there is no separate "label-drop" path that empties an owner list on a *live*, non-deleting VM: a VM's ownership can only end by the VM itself being deleted. See D9b.

### The provider's Kubernetes client is cached, so a create is not readable in the same reconcile

The provider is built with `mgr.GetClient()` (`pkg/manager/init/init_providers.go:19` → `vsphere.NewVSphereVMProviderFromClient`), and the session carries that same client as `Session.K8sClient`. The manager's client caches reads for every type except the three in `pkg/manager/manager.go`'s `Client.Cache.DisableFor` list — `corev1.ConfigMap`, `corev1.Secret`, `appsv1.Deployment`. `Tag` is therefore served from the informer cache.

Consequence for this design: within a single VM reconcile, a `Tag` created by the ensure step is **not** guaranteed to be returned by a subsequent `List` in the same pass — the informer will not have observed the create yet. Any step that derives the VM's desired tag set purely from a `List` would therefore miss the VM's own newly created `Tag`, and spec G1 / US1.1 would converge only on a later reconcile driven by the `Tag` watch. The fix is to union the `Tag` objects the ensure step already holds into the desired set rather than re-reading them; see `plan.md` "`ReconcileTagSpecs` — steps 4-5". This is a correctness requirement, not a latency optimization, and it is why the two halves of the VM path hand a value to each other instead of both reading from the cache.

Cross-VM participation is unaffected and legitimately relies on the cache plus the fan-out: a label-only VM learns about another VM's `Tag` on its own reconcile, which the `Tag` watch triggers once the `Tag` exists.

### The attached-tag list is UUIDs and is not on `moVM`, so the applied set is recorded in ExtraConfig

`vs.getTags` (`pkg/providers/vsphere/vmprovider_vm.go:1362`) is step 3 of the update flow. It calls `tags.NewManager(vcClient.RestClient()).ListAttachedTags`, which returns a `[]string` of **tag URNs**, and stashes it in the *context* via `pkgctx.WithVMTags` (`pkg/context/virtualmachine_context.go:154`), read back with `pkgctx.GetVMTags`. It is not placed on `moVM`, and it carries neither tag name nor category. (`mo.ManagedEntity.Tag` is the legacy pre-6.0 `vimtypes.Tag{Key}`, unrelated to tagging-service tags.)

Mechanism B is built around exactly this limitation, and its workflow is the prior art this feature follows (D12). `pkg/vmconfig/policy/policy_reconciler.go`:

- `const ExtraConfigPolicyTagsKey = "vmservice.policy.tags"` (line 29) — "the tag UUIDs that we have applied … so can later only remove tags that we have applied."
- On each reconcile it computes `shouldBe`, reads `haveBeen` from that ExtraConfig key, and takes `are` from `pkgctx.GetVMTags` (line 115-120).
- It appends the new `shouldBe` to `configSpec.ExtraConfig` **only when it differs** from the recorded value (lines 168-190), so the record is updated in the same reconfigure that applies the tag change — the record and the tags commit atomically.
- `pkg/providers/vsphere/virtualmachine/cleanup.go`'s `removeTagAssociations` reads the same key to emit removals when a VM is detached from the platform resource, and its comment notes that emitting a remove for a tag that is not actually attached is harmless: "Just because a tag is present in the ExtraConfig does not guarantee that it is also associated to the VM … Reconfigure will ignore these tags anyway."

This feature identifies its tags by name + category (D6), so it cannot compare the desired set against the attached URN list at all. It therefore keeps its **own** ExtraConfig key with the same workflow, and does not consult `pkgctx.GetVMTags`. Two details fall out:

- **Removals** are `haveBeen \ shouldBe`, not `(are ∩ haveBeen) \ shouldBe` as in mechanism B — the intersection with the attached list is not available, and per the comment above it was only ever an optimization.
- **Additions** are `shouldBe \ haveBeen`, not `shouldBe \ are`. Mechanism B self-heals a tag detached out-of-band in vCenter because it diffs against what is actually attached; this feature cannot, and must not compensate by re-emitting the whole `shouldBe` set every reconcile — that would make every fan-out reconcile issue a reconfigure and break the no-op property D9d depends on (`plan.md` "Fan-out — the VM controller's `Tag` watch"; tasks T022). An out-of-band detach is therefore not corrected until the desired set itself changes. Accepted; recorded as a limitation in `spec.md` "Edge cases".

Comma-joining is safe for this key: a Kubernetes label value admits only alphanumerics, `-`, `_` and `.`, and a label key adds only `/` and `.`, so no `<key>:<value>` string can contain a comma.

### `TagSpec` supports removal, so tags can be diffed

`vimtypes.TagSpec` embeds `ArrayUpdateSpec`, so `ArrayUpdateOperationRemove` is available alongside `add`. Combined with the attached-tag list the update flow already fetches, this makes the tag set a diff (add missing, remove extra) rather than an append-only operation — required by spec G5 and US3.

### vCenter Tag identity is name + category

vCenter Tags are unique per (name, category). This feature keeps today's convention: name `"<key>:<value>"`, category `<namespace>` (D6), which is what makes namespace isolation (spec G6) fall out for free and keeps the emitted `TagSpec`s interchangeable with the Compute Policy side, which builds `TagId.NameId` the same way in `buildTagIDsFromTopology`.

### Fan-in writes to a shared list field need an optimistic lock

Several VMs in a namespace add and remove their own entry in the same `Tag`'s `ownerReferences` — a fan-in write to a **list**-typed field. Per `operator-best-practices.md` ("Fan-out to Child Objects") and the constitution, a plain merge patch replaces list fields wholesale with no conflict detection and can silently drop a concurrent writer's entry, so these writes use `client.MergeFromWithOptions(base, client.MergeFromWithOptimisticLock{})`, compare with `apiequality.Semantic.DeepEqual`, and skip when nothing changed. `controllerutil.CreateOrPatch` is therefore **not** appropriate for the ownership write, despite being the repository default for fan-out.

### `client.MatchingLabels` is not an indexed lookup

controller-runtime's cache maintains **field** indexes only — those registered via `mgr.GetFieldIndexer().IndexField(...)`. A label selector passed to a cached client is applied as an **in-memory filter after** the cache has returned every object in the namespace; there is no label index to consult. (The API server behaves the same way for arbitrary labels on a direct, uncached `List`.)

Three consequences for this design:

1. The `Tag`'s `metadata.labels` mirror does **not** make the control plane's queries efficient. It is a convenience surface for `kubectl get tags -l app=nginx` and for legibility of a hash-named resource — worth keeping for those reasons, but it must not be the mechanism behind "does a `Tag` for this label exist?" on the reconcile hot path. That question is answered by a `Get` on the derived name instead, which is a point read.
2. The one other repeated `Tag` query gets an explicit field index: `metadata.ownerReferences.uid` (which `Tag`s a VM owns). The exact-pair case needs no index — the webhook pins the name to the pair and makes the pair immutable, so a keyed `Get` always resolves it, and every caller (including step 4's per-label lookup) already knows both the key and the value. See `plan.md` "Field indexes and query patterns" and `model.md` "Query surface".

3. The `Tag` watch's mapper — "which VMs carry this label?", the query spec US2 depends on — gets a field index too: `metadata.labels.keyValue` on `vmopv1.VirtualMachine`, whose extractor emits one `"<key>:<value>"` entry per label after `kubeutil.RemoveVMOperatorLabels`. The `List` then returns only the VMs carrying the label, so fan-out cost scales with the size of the affinity relationship rather than with the namespace's VM count.

A multi-valued extractor over label pairs is idiomatic in this repository, not exotic: `pkg/util/kube/pvc.go`'s `VMSpecVolumesPVCsIndexerFunc` already emits one entry per PVC a VM references, and `RemoveVMOperatorLabels` returns a fresh map (`pkg/util/kube/label.go`) so calling it from an extractor cannot mutate the cached object. Filtering the reserved `vmoperator.vmware.com`-domain labels out also keeps the index free of entries that could never match a `Tag`, since the same filter governs which labels can participate in affinity today.

Two claims in earlier drafts of this document were wrong and are retracted here:

- "The informer's label index serves this directly and no `IndexField` registration is needed" — there is no label index; see above.
- "A field index cannot be built over arbitrary label keys ... so the fan-out keeps an in-memory filter" — conflating *controller-runtime not maintaining a label index by default* with *a per-pair index being infeasible*. A custom multi-valued extractor supplies exactly that index at a cost proportional to the label maps already in cache, which is why the fan-out is indexed after all.

## Decision log

Decision IDs are stable: `D9a`-`D9d` are later insertions that keep the lettered suffix so earlier references to `D9` and `D10` elsewhere in these artifacts stay valid.

| # | Decision | Alternatives rejected |
|---|----------|-----------------------|
| **D1** | The `Tag` type is added to the existing external module `external/vsphere-policy/api/v1alpha1`, group `vsphere.policy.vmware.com`, version `v1alpha1`. Its controller goes under `controllers/vspherepolicy/tag/` and its webhook under `webhooks/vspherepolicy/tag/`. | Adding `Tag` to `api/v1alpha6` under `vmoperator.vmware.com`: rejected because the source spec's data model is explicit about the group/version, the type is conceptually part of the vSphere policy surface that already owns `TagPolicy`, and placing it there keeps it out of the DevOps-facing API group (spec G9). Cost accepted: the type lives in a module whose upstream owner is outside this repository, so future upstream changes must be reconciled. |
| **D2** | The VM reconcile path owns `Tag` resources and vCenter tag application; the `Tag` controller fans out. Concretely: a new `vmconfig` reconciler creates/patches the `Tag`, maintains its **own** VM's owner reference, and emits the `TagSpec` add/remove diff; the `Tag` controller owns `Tag` status, its finalizer, its delete-at-zero-owners decision, and enqueuing every affected VM in the namespace. | Making the `Tag` controller derive ownership for *all* VMs itself (list VMs, compute the full owner set, write it): rejected because it makes the `Tag` controller a second writer of state each VM's own reconcile already computes, duplicating the affinity-term walk and creating a two-writer race on `ownerReferences` with no single authority per entry. The chosen split gives exactly one writer per owner-reference entry. |

| **D9a** | Ownership and tag carriage are two **different** predicates: a VM owns a `Tag` iff its own `spec.affinity` references it (D9b); a VM carries the vCenter tag iff it carries the label **and** a `Tag` for the pair exists. Tag carriage never consults the VM's own affinity, and ownership never consults carriage. | The source spec was internally contradictory here: US2.1 tagged a VM carrying the label with no affinity of its own, while the original US3 untagged a VM carrying the label that had ceased to be an owner — the same live state (carries the label, is not an owner, another VM owns the `Tag`) with opposite outcomes, distinguishable only by history a level-triggered reconciler does not keep. Rejected alternative 1, "tagged unless the VM declares affinity that excludes the label": would have satisfied both scenarios as written and is history-free, but it silently drops a VM out of a relationship it still carries the label for, defeating the other VMs' stated affinity toward it. Rejected alternative 2, "owners only": would have deleted US2 and with it the feature's main new capability (spec G2). Resolution: label match alone wins for carriage, and US3 was rewritten in `spec.md` — a VM that carries a participating label without owning the `Tag` is an ordinary label-only participant, however it got there. |
| **D9b** | A `Tag` is created for every pair a VM's own `spec.affinity` references, whether or not the VM carries it. A VM can own a `Tag` for a pair it never carries. | An earlier version of this decision created a `Tag` only for a pair a VM both carried and referenced, rejecting the alternative below on the reasoning that it "widens `Tag` creation to labels no VM in the namespace is available for." The relationship the referencing VM asked for was silently unenforceable. Confirmed with the user (walking through a concrete VM-A/VM-B/`lbl2` scenario): the referencing VM should own the `Tag` regardless of carriage, and should **not** itself gain the vCenter tag purely from owning it — tag carriage stays exactly as D9a states. This retires the "last owner drops the label" deletion trigger from the original US3 (see spec.md's rewritten US3 and the "Owner-reference garbage collection" note above); the sole remaining deletion trigger is every owning VM being deleted (US1 scenario 6). |
| **D9c** | `Tag` lookups are served by two mechanisms: a `Get` on the derived name for exact-pair existence, used by every controller-side query including step 4's per-label desired-set computation, and the `metadata.labels` mirror for `kubectl` only. No index covers the exact pair, because validation makes the derived name an invariant — the name is pinned to the pair on create and both fields are immutable thereafter, so the keyed `Get` can never fail to find a `Tag` that exists. | Relying on the `metadata.labels` mirror with `client.MatchingLabels` for the control plane's own queries: rejected because it is an in-memory filter over the whole namespace, not an index (see above) — it would make the most frequent query in the feature O(all `Tag`s in the namespace) while looking like an indexed lookup in the code. Dropping the mirror entirely: rejected because it is the only way to select `Tag`s by label from `kubectl` and the only thing that makes a hash-named resource legible at a glance. A field index on `spec.key` for key-wide lookups: rejected — every caller of a `Tag` query in this feature already knows both the key and the value it wants (the VM's own label, or `ReconcileTagCRs`' owned pair), so a `Get` on the derived name always suffices and a key-wide index has no caller. |
| **D9d** | The fan-out's query — "give me the VMs carrying this `Tag`'s label" — is served by a multi-valued field index `metadata.labels.keyValue` on `vmopv1.VirtualMachine` (one `"<key>:<value>"` entry per non-VM-Operator label), so it returns matches only. The mapper then enqueues **every** matching VM, accepting that most resulting reconciles are no-ops. | Filtering in memory with `client.MatchingLabels`: rejected — it returns every VM in the namespace from the cache and filters afterward, so a query that runs on every `Tag` create and delete would scale with namespace size instead of relationship size, and `operator-best-practices.md` requires the indexed form in a mapper. Enqueuing only the VMs whose tag set actually changed: rejected because that would have to reproduce each VM's tag diff against a stale view, duplicating the VM path's logic and re-introducing the two-writer problem D2 exists to avoid; an indiscriminate fan-out plus an idempotent no-op reconcile is both simpler and safer. Workqueue de-duplication and the skip-if-unchanged guard keep the no-op path read-only, so it cannot loop. |
| **D10** | The `Tag` controller carries **no finalizer**. `Delete`s the `Tag` outright — preconditioned on `ResourceVersion` so a concurrently-added owner reference wins the race instead of being silently destroyed — when it observes an empty `ownerReferences` list, and the resulting delete event is what the VM controller's `Tag` watch fans out on (D19). | An earlier version of this decision held a finalizer and enqueued affected VMs itself before removing it, reasoning that label-only VMs otherwise had nothing to tell them to drop the vCenter tag. That reasoning didn't survive D19: once fan-out moved to the watch, the finalizer stopped doing any fan-out work — `ReconcileDelete` removed it unconditionally, on the very next reconcile, without waiting for anything — so it manufactured an observable "terminating" state (`deletionTimestamp` set, object still present) purely so `ReconcileTagCRs`/`desiredTagSet` could react to it, a problem that existed only because the finalizer existed to be reacted to. It also introduced a real hazard absent from the atomic-delete design: `CRDCleanupEnabled=true` deleting the CRD while `Tag`s hold this finalizer and `TaggingAPI` is off wedges every affected namespace's termination until the finalizers are cleared by hand (unlike `PolicyEvaluation`, whose finalizer's owning controller is never off in a configuration that also deletes its CRD). Retaining the finalizer purely to widen the window for the owner-reference race above: rejected because `ReconcileDelete` never rechecked owners before removing it, so the finalizer was not actually a guard against that race either — the guard is the `Delete` precondition, which works with or without a finalizer. |
| **D11** | The VM path is dispatched from **two** explicit call sites in `doReconfigure`, straddling `reconcileVSpherePolicies`: `ReconcileTagCRs` (ensure `Tag`s + ownership) before it, `ReconcileTagSpecs` (desired set + `TagSpec` diff) after it. | **D12** | This feature records the `<key>:<value>` tags it has applied in its own VM ExtraConfig key, a different key from mechanism B's `vmservice.policy.tags` but with the same workflow: diff `shouldBe` against the recorded `haveBeen`, and write the new record into the same `configSpec` that applies the tag change. | Diffing against the attached-tag list from `pkgctx.GetVMTags`: rejected because that list is tag URNs with no name or category, so this feature's name+category tags cannot be found in it (see above). ## Open follow-ups (not part of this feature)

- Remove `genConfigSpecTagSpecsFromVMLabels` and its call sites once the `Tag`-driven path is GA (spec NG4, D4).
- Populate the `Tag`'s reserved vCenter Tag UUID field once something needs the resolved UUID (spec NG1); today's tag attachment is name+category-based and does not.
- Remove the `VirtualMachineGroup` dependency from affinity end to end (spec NG3, SC-004).
- Make `spec.affinity` mutable (spec NG8, D7). Blocked on the placement-hint gap: a `TagSpec` naming a tag that does not yet exist in vCenter fails with `cis.tagging.objectNotFound.error`, and only the `VmPlacementPolicies` a VM is placed with cause `vpxd` to provision one. Unblocking it means either provisioning the vCenter tag explicitly (a vCenter-side write this feature deliberately does not do — spec NG1) or emitting a placement-policy hint from the update path. Until then, re-pointing a running VM's affinity requires a re-create.

The `PlacementPoliciesForVMServiceVmsV3` capability target itself (spec G13) is decided, not deferred — wiring `Features.TaggingAPI` to a `CapabilityKeyPlacementPoliciesForVMServiceVmsV3` entry in `pkg/config/capabilities/capabilities.go`, and returning the development-branch default to `false`, is pending implementation as part of this feature (D3) rather than an open follow-up.
