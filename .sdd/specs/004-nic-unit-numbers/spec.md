## Goals

- MUST: A `spec.network.interfaces[i].unitNumber` field MUST be supported that identifies each NIC's slot on the virtual PCI bus (values 7–16; vSphere assigns ethernet cards unit numbers starting at 7 because the lower slots on the shared virtual PCI bus are occupied by other devices such as the video card and storage controllers).
- MUST: `unitNumber` is optional and MUST NOT be auto-assigned by the mutation webhook. There is no webhook-side slot computation at all. When the user explicitly sets a value, the `VirtualEthernetCard` device MUST be created with that unit number; when the field is unset, vSphere assigns the slot at device-creation time and the schema-upgrade backfill (below) records the observed value into the spec after the VM is created. Because the webhook never guesses values, there is no ordering race between webhook assignment and the backfill.
- MUST: The validation webhook MUST reject specs where two interfaces share the same `unitNumber`, where the value is out of range (7–16), and (on update) where a previously-set unit number is changed to a different value while the VM is powered on (nil → set transitions MUST be allowed — the backfill writes observed values into the spec of running VMs). When the `VMNetworkUnitNumbers` flag is disabled, any use of the field MUST be rejected with `field.Forbidden` (same pattern as `validateNetworkVLANs`), so stale or duplicate values cannot be persisted while the feature is off and later poison the spec-wins backfill. Decision (2026-07-27): disabling the feature after the backfill has run is not a supported flow (see Non-goals), so this reject rule needs no carve-out for previously-backfilled values.
- MUST: `status.network.interfaces[i].unitNumber` MUST reflect the observed unit number from vSphere after each reconcile, for every interface reported in guest info. (Note: interface status entries are built from VMware Tools guest info; interfaces not reported by Tools do not appear in `status.network.interfaces` at all, so this criterion only applies to VMs with Tools running.) Population of the status field MUST be gated behind the `VMNetworkUnitNumbers` flag: when the flag is off, `status.network.interfaces[i].unitNumber` is not written.
- MUST: `spec.network.interfaces[i].unitNumber` MUST be backfilled during schema upgrade from the live vSphere VM configuration, preferring the existing MAC address / ExternalID / backing hodgepodge to match spec interfaces to VC devices and falling back to a positional zip for otherwise-unmatched devices. This single mechanism covers **both** brownfield VMs (on operator upgrade) and greenfield VMs (on their first post-create reconcile, once the vSphere devices exist). The backfill MUST run even when `spec.network.disabled` is true — a disabled-network VM has no ethernet devices, so nothing is recorded and the feature-version bit is still stamped (one-shot semantics are preserved). The backfill MUST be a standalone schema-upgrade step with its own feature-version bit (`FeatureVersionNICUnitNumbers`); it MUST NOT live inside `NICConfigFromMoVM` under the `TelcoVMServiceAPI` gate, because that gate is one-shot — VMs already stamped with the Telco bit would never be backfilled — and because `TelcoVMServiceAPI` may be disabled while `VMNetworkUnitNumbers` is enabled.
- MUST: After the backfill, NIC reconcile MUST use `unitNumber` (when set on the spec interface) as the primary stable match key against the VC VM's ethernet devices, both when deciding what changes to send to vSphere (`ReconfigVM_Task`) and when mapping device keys to spec indices for status. A unit-number match identifies the device; the reconciler MUST then diff the matched device against the desired state and emit the appropriate `VirtualDeviceConfigSpec` entries — an Edit for backing/property changes, or a Remove of the matched device plus an Add of the desired device at the same unit number when the device type differs — so the VM's hardware configuration converges to the spec. Matching MUST be two-pass: interfaces carrying a `unitNumber` claim their matching devices first, and only then are the remaining interfaces matched via the MAC/ExternalID/backing fallback, so an interface without a unit number can never claim (via backing match) a device whose slot another interface explicitly requests. This applies to `ReconcileNetworkInterfaces`, to the post-reconfigure fixup pass (`fixupMacAddressMutableNetworks`), and to `MapEthernetDevicesToSpecIdx`.
- MUST: Sending a desired `unitNumber` to vSphere on an Add config spec (so vSphere places the NIC at the desired slot) MUST be gated on research confirming vSphere honours the field.
- MUST: The VM create path MUST set `unitNumber` on each NIC device whose spec interface carries an explicit value, under the same research gate as the reconcile Add path, so explicitly-placed NICs land at their requested slots from first boot. The initial `ConfigSpec`'s NIC devices come from **two** branches, and both MUST honour the explicit value: (a) ethernet devices originating in the VM class ConfigSpec, positionally applied to spec interfaces via `ApplyNetworkDeviceToVirtualEthCard` — an explicit spec value overrides any unit number already present on the class device (spec wins); and (b) default devices built via `CreateDefaultEthCardFromNetworkDevice` for spec interfaces with no class device. Interfaces without an explicit value are created without a spec-driven unit number (a class-device unit number, if present, is left as-is) and receive vSphere's assignment, which the post-create backfill then records into the spec.
- MUST: Older API versions (v1alpha5 and earlier) MUST round-trip the new spec field via the annotation-based conversion restore mechanism, so an UPDATE submitted by an old-version client does not wipe `spec.network.interfaces[i].unitNumber`. **Each of `v1alpha2`, `v1alpha3`, `v1alpha4`, and `v1alpha5` has its own `restore_v1alpha6_VirtualMachineNetworkInterfaces`** (each restores `vnumaNodeID` today) and all four MUST be extended. `v1alpha1` restores the entire interfaces list wholesale when the down-converted list is non-empty, so it needs no per-field change, but its conversion fuzz tests MUST assert the field survives the round-trip.
- MUST: The unit-number-based matching and schema-upgrade backfill MUST be gated behind the `VMNetworkUnitNumbers` feature flag.
- SHOULD: A govmomi research program SHOULD be written and executed against a real vCenter to validate vSphere's unit-number behaviour before the matching logic is finalised.

## Non-goals

- This spec does NOT introduce a new "NIC controller" CRD or API object. NICs remain modelled as a flat list on the single implicit virtual PCI bus (bus 0, always present, not represented in `spec.hardware`).
- This spec does NOT change how network provider CRs (NetOP, NCP, VPC) function. The unit number is a vSphere-layer identifier only; provider CRs are unchanged.
- This spec does NOT address SR-IOV physical/virtual function passthrough placement. Note, however, that SR-IOV NICs in `spec.network.interfaces` are still ethernet cards on the virtual PCI bus and ARE covered by unit-number assignment, validation, backfill, and matching like any other interface type (`pkgutil.IsEthernetCard` includes `VirtualSriovEthernetCard`).
- This spec does NOT remove or replace the existing MAC address / ExternalID / backing matching. Unit number becomes a new primary key; the existing logic is retained as a fallback for interfaces that do not yet have a unit number.
- This spec does NOT change the immutable-networks positional-zip path beyond adding unit-number matching as a preferred alternative when unit numbers are present.
- This spec does NOT support disabling the `VMNetworkUnitNumbers` feature once the backfill has populated unit numbers into VM specs. The validation webhook rejects any use of the field while the flag is off — including previously-backfilled values — so spec updates to those VMs would fail until the flag is re-enabled. Rolling the feature off after rollout is not an expected operational flow (decision 2026-07-27).

## User stories / acceptance criteria

### DevOps user

- **Given** a new VM with `spec.network.interfaces` and no `unitNumber` set, **When** the VM is created and first reconciled, **Then** the spec is unchanged at admission time (the mutation webhook does not assign unit numbers), vSphere assigns slots starting at 7 when the devices are created, and the post-create backfill records the observed values into `spec.network.interfaces[i].unitNumber`.
- **Given** a new VM where one interface explicitly sets `unitNumber: 9`, **When** the VM is created, **Then** the NIC device in the initial `ConfigSpec` carries unit number `9` and vSphere places it at that slot (honouring confirmed by T001); the remaining interfaces receive vSphere-assigned slots which the backfill records into the spec.
- **Given** two interfaces with the same `unitNumber`, **When** the user submits the VM, **Then** the validation webhook rejects the request with a clear, field-specific error message.
- **Given** a `unitNumber` value outside 7–16, **When** the user submits the VM, **Then** the validation webhook rejects the request with a range error.
- **Given** a powered-on VM, **When** the user tries to change an existing interface's `unitNumber`, **Then** the validation webhook rejects the change.
- **Given** a VM after reconcile, **When** the user inspects `status.network.interfaces`, **Then** each entry carries a `unitNumber` matching the slot observed in vSphere.

### Platform engineer

- **Given** a brownfield VM with no `unitNumber` on any interface, **When** VM Operator is upgraded and the VM is next reconciled (with the `VMNetworkUnitNumbers` flag enabled), **Then** the schema upgrade backfills `unitNumber` into each `spec.network.interfaces[i]` from the vSphere `VirtualDevice.UnitNumber`, matched using the existing MAC / ExternalID / backing approach with a positional-zip fallback for otherwise-unmatched devices.
- **Given** a VM whose schema upgrade has already stamped `FeatureVersionNICUnitNumbers`, **When** a NIC is later added to `spec.network.interfaces` without an explicit `unitNumber`, **Then** the spec field remains nil for that interface (the backfill is one-shot and does not re-run), vSphere assigns the slot, `status.network.interfaces[i].unitNumber` reports the observed value, and the interface is matched via the existing MAC / ExternalID / backing fallback.
- **Given** a VM with `unitNumber` backfilled and the feature flag enabled, **When** an interface is reconciled against vSphere, **Then** the reconciler uses `unitNumber` as the primary match key instead of the backing/ExternalID hodgepodge, avoiding spurious remove+add cycles.
- **Given** a VM where a NIC is added to `spec.network.interfaces`, **When** the reconciler runs (flag enabled), **Then** the new NIC is added to vSphere at the unit number specified in the spec (if vSphere honours explicit placement — confirmed by research), and the status reflects the observed unit number afterward.
- **Given** a VM where a NIC is removed from `spec.network.interfaces`, **When** the reconciler runs (flag enabled), **Then** the correct VC device is removed (identified by unit number), and the remaining NICs retain their unit numbers in both spec and status.

## Resolved questions

- **RESOLVED**: vSphere assigns the first NIC unit number **7**. NICs occupy slots 7–16 on the shared virtual PCI bus; the slots below 7 are used by other virtual devices (video card, controllers, etc.). T001 should still confirm this starting slot is stable across the vSphere versions we support.

- [NEEDS CLARIFICATION: Can a NIC's unit number be changed on a powered-off VM via an Edit config spec? — to be answered by T001.]
- [NEEDS CLARIFICATION: When a NIC is removed and a new one is added, does vSphere reuse the old slot or assign the next available?]
- [NEEDS CLARIFICATION: Are NIC unit numbers stable across VM power cycles?]
- [NEEDS CLARIFICATION: What happens to unit numbers when a user adds a NIC via the vCenter UI (bypassing vm-operator)?]
- [NEEDS CLARIFICATION: If T001 shows vSphere does NOT honour explicit placement on Add, how does a greenfield spec value ever converge with the observed slot? The schema-upgrade backfill is one-shot and spec-wins, so it cannot correct an already-set spec value — the design for that branch must be revisited (e.g., limit unit-number-first matching to backfilled VMs, or define a sanctioned spec-correction write).]
- [NEEDS CLARIFICATION: Does vSphere honour an explicit `unitNumber` on a hot-add (NIC added to a powered-on VM)? The validation webhook allows adding a new interface with an explicit value while powered on — to be answered by T001.]
- [NEEDS CLARIFICATION: Do SR-IOV ethernet cards (`VirtualSriovEthernetCard`) occupy the same 7–16 unit-number space on the virtual PCI bus as other NIC types? The spec asserts SR-IOV NICs are covered by the same assignment/validation/matching — to be confirmed by T001.]
- [NEEDS CLARIFICATION: What fault does vSphere return when an explicit unit number collides with an existing device (vcsim returns `InvalidDeviceSpec`)? This drives the reconciler's error handling for a failed Add — permanent-error (`NoRequeueError`) vs. retry — to be answered by T001. A collision is possible despite webhook uniqueness validation, e.g. against a class-ConfigSpec device or a NIC added out-of-band via the vCenter UI.]
- [NEEDS CLARIFICATION: Snapshot revert interplay (T031). `restoreVMSpecFromSnapshot` restores the VM spec and annotations (including the feature-version annotation) from the backup yaml stored with the snapshot, so unit numbers and the backfill bit travel with the snapshot; the imported-VM fallback synthesizes interfaces without unit numbers. Reverting to a pre-backfill snapshot drops the bit and re-triggers the backfill — verify this converges correctly.]
